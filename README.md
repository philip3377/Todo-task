# TaskFlow API

A beginner-friendly Task Management REST API built with Node.js, TypeScript, and Express.

The main purpose of this project is to serve as a safe playground for **GitLab CI/CD pipelines**, **automated dependency updates**, and **security scanning** experiments. The application itself is intentionally simple: an in-memory task store with clean layering (routes → controllers → services), input validation, centralized error handling, and security headers.

### Why the code is layered this way

- **routes** only decide *which URL maps to which function*.
- **controllers** translate between HTTP (request/response/status codes) and the service.
- **services** hold the business logic and the data store, with no Express imports — that is why they are easy to unit test.
- **middleware** provides cross-cutting behavior (validation helpers, error handling) that applies to every request.

## Web UI

This project is a **monolith**: one Express server serves both the web UI and the JSON API on the same port. Open `http://localhost:3000` after starting the server (dev or compiled mode).

What the UI includes:

- A "work order board" styled task list (industrial paper/ink/signal-yellow theme, custom CSS, no CSS framework).
- Create tasks ("issue a work order") with title and optional notes, with inline validation errors.
- Toggle tasks done with a checkbox — completed tasks get a rotated **DONE** stamp.
- Edit title and notes inline per card (with its own validation), cancel anytime.
- Delete with a two-click confirm (the ✕ button changes to "SURE?" for 2.5 seconds).
- Filters (All / Active / Done) with live counts, and a board summary line.
- A live API status lamp fed by `GET /api/health` (polls every 15 seconds), plus an error banner with Retry if the server is unreachable.
- Keyboard-accessible controls, visible focus rings, responsive layout down to phone width, and `prefers-reduced-motion` support.

How it works:

- `src/app.ts` mounts `express.static` on the `public/` folder, so `GET /` returns `index.html` and the browser loads `/styles.css` and `/app.js` from the same origin.
- `public/app.js` is plain browser JavaScript (no framework, no build step). It calls the same REST API documented above using `fetch` and renders tasks by creating DOM nodes with `textContent` — task content is never injected as raw HTML, so stored XSS via task titles is not possible.
- Helmet's Content Security Policy applies to the page too: only same-origin scripts are allowed (which is why there are no inline `<script>` handlers), plus Google Fonts stylesheets/files from `https:`.
- The UI only renders what the API returns after validation; the browser never talks to storage directly.

## API Reference

Base URL: `http://localhost:3000/api`

All responses are JSON. Errors always use the same shape:

```json
{
  "error": {
    "status": 400,
    "message": "\"title\" is required and must be a non-empty string"
  }
}
```

### Health

#### `GET /api/health`

```bash
curl http://localhost:3000/api/health
```

```json
{
  "status": "ok",
  "uptime": 5.5343435,
  "timestamp": "2026-11-06T04:00:58.829Z"
}
```

### List all tasks

#### `GET /api/tasks`

```bash
curl http://localhost:3000/api/tasks
```

Returns `200` with an array (empty when the store is fresh):

```json
[]
```

### Get one task

#### `GET /api/tasks/:id`

```bash
curl http://localhost:3000/api/tasks/cf31ba37-70c0-444f-b4ab-341309d59582
```

Returns `200` with the task, or `404` if the id does not exist:

```json
{
  "id": "cf31ba37-70c0-444f-b4ab-341309d59582",
  "title": "Smoke test task",
  "description": "created via smoke test",
  "completed": false,
  "createdAt": "2026-11-06T04:00:38.859Z"
}
```

### Create a task

#### `POST /api/tasks`

```bash
curl -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "Write CI pipeline", "description": "Set up .gitlab-ci.yml", "completed": false}'
```

Returns `201` with the created task.

Validation rules:

- The body must be a JSON object.
- `title` is required, must be a non-empty string, maximum 200 characters after trimming.
- `description` is optional, maximum 2000 characters (defaults to `""`).
- `completed` is optional, must be a boolean (defaults to `false`).
- Unknown fields (e.g. `isAdmin`) are silently dropped — the server only accepts the whitelisted fields.
- String values are trimmed, and requests larger than 16 KB are rejected with `413`.

### Update a task

#### `PUT /api/tasks/:id`

```bash
curl -X PUT http://localhost:3000/api/tasks/cf31ba37-70c0-444f-b4ab-341309d59582 \
  -H "Content-Type: application/json" \
  -d '{"completed": true}'
```

Returns `200` with the updated task, `400` if the body is empty or invalid, `404` if the id does not exist. Only provided fields change; `createdAt` and `id` never change.

### Delete a task

#### `DELETE /api/tasks/:id`

```bash
curl -X DELETE http://localhost:3000/api/tasks/cf31ba37-70c0-444f-b4ab-341309d59582
```

Returns `204` with no body on success, `404` if the id does not exist.

### Malformed JSON

Sending invalid JSON returns `400` without a stack trace:

```json
{
  "error": {
    "status": 400,
    "message": "Unexpected token } in JSON at position 10"
  }
}
```

## Dependency Auditing with npm audit

```bash
npm audit                        # summary of known vulnerabilities
npm audit --audit-level=high     # exit code 1 if any high or critical issue exists (used in CI)
npm audit fix                    # install compatible patched versions
npm audit fix --force            # also apply breaking major upgrades (review carefully)
```

### Notes from this repository

- All critical/moderate findings were resolved before release; `npm audit --audit-level=high` currently reports **0 vulnerabilities**.
- `package.json` contains an [`overrides`](https://docs.npmjs.com/cli/v10/configuring-npm/package-json#overrides) entry that forces `minimatch` to a patched version because two tools (ESLint and typescript-eslint) pinned a vulnerable transitive range. This is a common, safe technique — check the override in the [npm advisory](https://github.com/advisories) you are fixing, then remove the override once the parent packages catch up.

## How the GitLab CI/CD Pipeline Works

Defined in `.gitlab-ci.yml`:

```text
Stage: install      Stage: test                          Stage: security   Stage: build
--------------      ---------------------------------    ---------------   -------------
install             lint, typecheck, test (parallel)     audit             build
```

| Job | Stage | Script | Purpose |
|---|---|---|---|
| `install` | install | `npm ci --prefer-offline` | Reproducible install from `package-lock.json`; saves `node_modules/` as 30-minute artifacts |
| `lint` | test | `npm run lint` | Code quality |
| `typecheck` | test | `npm run typecheck` | TypeScript type safety |
| `test` | test | `npm test` | Runs the Vitest suite (fails the pipeline on any failing test) |
| `audit` | security | `npm audit --audit-level=high` | Blocks the pipeline on high/critical vulnerabilities |
| `build` | build | `npm run build` | Compiles TypeScript; uploads `dist/` as artifacts (1 week retention) |

Key properties:

- **Image**: every job uses the official `node:24-alpine` Docker image. No privileged Docker access, no custom images, no services.
- **When pipelines run**: on every branch push and on merge requests. The `workflow: rules` section prevents duplicate pipelines when a branch already has an open merge request.
- **Caching**: npm's download cache lives in `.npm/` and is keyed on `package-lock.json`, so it resets automatically when dependencies change. Between pipelines it comes from GitLab's distributed cache.
- **Artifacts vs cache**: `node_modules/` passes from `install` to later jobs as *artifacts* (exact contents guaranteed), while `.npm/` is *cache* (a speed optimization only). `dist/` is kept as a 1-week artifact so you can download the compiled result.
- **No deployment**: there is deliberately no production deployment stage. The pipeline stops after building.

## Inspecting Failed Pipeline Jobs

1. Open your project on GitLab → **Build → Pipelines** (or the pipeline widget on a merge request).
2. Each pipeline row shows stages as icons. A red stage contains a failed job — click it.
3. Click the **failed job name** (e.g. `test#123456`) to open its console log.
4. Read the log from the bottom up; the failing command and its output are at the end. Common cases:

| Failing job | Typical log line | Usual cause and fix |
|---|---|---|
| `install` | `npm error code EUSAGE` / lock file mismatch | `package.json` and `package-lock.json` disagree. Run `npm install` locally and commit the updated lock file |
| `lint` | `error 'x' is defined but never used` | ESLint finding. Fix the reported file, or run `npx eslint . --fix` locally |
| `typecheck` | `error TS2345: Argument of type ...` | Type error. Fix locally — `npm run typecheck` reproduces it |
| `test` | `FAIL tests/...` + `AssertionError` | A test failed. Run `npm test` locally to reproduce |
| `audit` | `vulnerability found: ... severity: high` | A dependency has a high/critical CVE. Run `npm audit` locally, then `npm audit fix` or add a reviewed `overrides` entry |

5. After fixing, push again — or click **Retry** on the job to re-run it unchanged.
6. Every pipeline is also visible per merge request, with job statuses summarized in the MR widget.

## Security Features of the Application

- **No hardcoded secrets** — nothing to leak; the app needs no credentials.
- **Input validation and sanitization** (`src/middleware/validate.ts`) — strict types, length limits, trimming, unknown-field whitelisting, 16 KB body cap.
- **Safe error responses** (`src/middleware/errorHandler.ts`) — consistent JSON errors, no stack traces, and internal messages are hidden when `NODE_ENV=production`.
- **Security headers** via Helmet (verified live): `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy`, and more.
- **No real vulnerabilities introduced** — the codebase contains no injection-prone patterns such as `eval`, `child_process` on user input, or raw SQL. The UI renders task content with `textContent` (never raw HTML), and Helmet's CSP blocks inline scripts.
- **Locked dependencies** — `package-lock.json` committed; CI installs with `npm ci`; audits gate the pipeline.

## GitLab Security Scanning (SAST, Secret Detection, Dependency Scanning)

Each scanner is a separate CI template that you can enable independently by adding an `include` block to `.gitlab-ci.yml`. Enable only the ones you want.

### Tier and runner requirements (important)

| Scanner | Minimum GitLab tier | Runner requirement |
|---|---|---|
| SAST | **Free** (basic scanning; Advanced SAST and MR findings need Ultimate) | Linux runner with Docker or Kubernetes executor — GitLab.com shared runners already satisfy this |
| Secret Detection | **Free** (customization and MR findings need Ultimate) | Same as above |
| Dependency Scanning | **Ultimate only** | Same as above |

On **GitLab.com** (SaaS), hosted runners run these jobs out of the box — no runner setup needed. On **GitLab Self-Managed**, you must register at least one Linux runner with the Docker or Kubernetes executor. On the Free tier, scan results are delivered as downloadable JSON artifacts; Ultimate additionally shows findings in merge requests, the security dashboard, and vulnerability reports.

### Enable SAST only

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
```

This adds a `sast` job that scans your TypeScript/JavaScript for known-vulnerable code patterns using open-source analyzers (Semgrep-based).

### Enable Secret Detection only

```yaml
include:
  - template: Jobs/Secret-Detection.gitlab-ci.yml
```

This adds a `secret_detection` job that scans commits for accidentally committed credentials (API keys, tokens, private keys).

### Enable Dependency Scanning only (Ultimate required)

```yaml
include:
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
```

This adds a `dependency_scanning` job that detects your npm dependencies and matches them against the GitLab Advisory Database. On the Free tier this job is not available — use `npm audit` (already wired into the `audit` job) as the Free-tier equivalent.

### Enable all three

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Secret-Detection.gitlab-ci.yml
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
```

Nothing else changes: the scanner jobs bring their own container images, run on the shared runners, and attach JSON report artifacts to the pipeline. Free-tier users see the reports as job artifacts; Ultimate users additionally get them rendered in merge requests and the security dashboard.

## Automated Dependency Updates

This project is designed as a target for dependency-update automation. Options that work with GitLab:

- **Renovate** (recommended): install the Renovate app for GitLab or run the `renovate` image in a scheduled pipeline. It opens merge requests that bump `package.json`/`package-lock.json`, and the pipeline in this repo validates each update automatically (install → lint → typecheck → tests → audit → build).
- **GitLab scheduled pipeline**: create a schedule (Build → Pipeline schedules) that runs a job with `npm outdated` or `npm update` and pushes a branch when updates exist.
- **Manual cadence**: periodically run `npm outdated` and `npm update` locally, then push — the pipeline gates the change exactly like any other contribution.

Because every update runs through the full pipeline, an update that breaks tests or introduces a high-severity vulnerability is rejected automatically.
